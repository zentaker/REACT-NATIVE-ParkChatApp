# ParkChat / Aldea — Hoja de Ruta de Producto, Migración y App Funcional de Grafos
Fecha: 2026-05-23
Documento de trabajo para gestionar el proyecto en Replit/GitHub y llevar la app desde MVP funcional hasta una red social geoespacial con grafo social. El producto se inspira en patrones de UX de apps como NomadTable, pero el diferencial de Aldea es que la unidad social principal no es el viaje ni el evento: es el lugar físico.
Nota legal/producto: el objetivo es lograr paridad de experiencia, claridad visual y dinámica social comparable, no copiar logos, marca, assets, screenshots, copy exacto, iconografía propietaria ni trade dress de terceros.
## 1. Resumen ejecutivo
Aldea es una app móvil de comunidad geoespacial. Cada parque, café, plaza, coworking, universidad o barrio puede tener un espacio digital propio con chat público, grupos, eventos espontáneos y relaciones persistentes entre personas, temas y lugares. La visión final es una app funcional de grafos: las interacciones no se quedan como mensajes aislados, sino que se convierten en conexiones consultables entre usuarios, lugares, conversaciones, grupos, eventos y temas.
La secuencia de validación sigue siendo:
lugar físico → conversación pública → grupo/evento → relaciones persistentes → grafo social geoespacial
La estrategia técnica recomendada es incremental: Supabase/Postgres para el MVP, edge events relacionales para preparar grafo, y Neo4j/AuraDB cuando la actividad social ya justifique consultas de profundidad, recomendaciones y visualización de conexiones.
## 2. Posicionamiento
Posicionamiento corto:
Aldea es una red social geoespacial donde cada lugar tiene una comunidad viva: chat local, grupos, eventos espontáneos y conexiones reales entre personas, temas y espacios.
Diferencia central frente a NomadTable-style products:
| Producto / patrón | Centro de gravedad | Cómo se traduce en Aldea |
| --- | --- | --- |
| NomadTable-style | Viajes, actividades cercanas, viajeros y meetups | Se toma como referencia de UX social: descubrimiento rápido, perfiles, actividades, chat y seguridad. |
| Aldea / ParkChat | Lugares físicos persistentes | Cada lugar tiene memoria social: chat, grupos, eventos, temas y conexiones que sobreviven al momento. |

## 3. Supuestos competitivos y UX inspiracional
Las fuentes públicas de NomadTable describen una experiencia enfocada en encontrar personas mientras viajas solo, ver actividades cercanas, unirte o crear actividades, ver personas cercanas, planear futuros viajes, usar mensajes/grupos, recomendaciones de actividades y perfiles verificados. Aldea tomará esos patrones de claridad y acción rápida, pero cambiará la lógica: en vez de “viaje/evento primero”, será “lugar primero”.
| Patrón UX inspirado | Lo que se busca conservar | Adaptación Aldea |
| --- | --- | --- |
| Nearby discovery | Sensación de “hay gente/planes cerca” | Mapa/lista de lugares vivos con actividad agregada. |
| Activity cards | Acciones rápidas: join/create | Eventos nacen desde un lugar o desde una conversación. |
| Group chats | Coordinación social inmediata | Chat público por lugar + chats de grupo. |
| Profiles + verification | Confianza para encuentros físicos | Perfil, safety mode, reportes, verificación futura. |
| Travel/social look | UI ligera, friendly, mobile-first | Sistema visual propio: cards redondas, chips, CTA claros, mapa/lista. |
| Premium discovery | Más alcance y visibilidad | Futuro: grupos destacados, eventos verificados, tools para organizadores. |

## 4. Principios de producto
- Space-first: la unidad primaria es el lugar, no el feed global.
- Safety-first: no se muestra ubicación exacta de usuarios; la presencia se comunica de forma agregada o contextual.
- Conversation-first: el chat público por lugar es el corazón del MVP.
- Graph-ready: guardar relaciones desde el día uno, aunque Neo4j llegue después.
- Mobile-first: Expo Go y teléfono físico son validación clave para UX y ubicación.
- No dating default: la app debe sentirse comunitaria, no romántica ni marketplace.
- Visual parity without copying: emular claridad de flujo y energía social, no activos propietarios.

| Capa | Implementación | Criterio de aceptación |
| --- | --- | --- |
| Reportes | safety_reports para mensaje/usuario/lugar/grupo/evento. | Usuario puede reportar y queda audit trail. |

## 16. Stage 4A — Graph-ready en Postgres
Antes de Neo4j, Aldea debe guardar eventos de relación de forma consistente. Esto permite aprender qué relaciones realmente tienen valor.
| Tabla / entidad | Propósito | Ejemplo |
| --- | --- | --- |
| graph_nodes | Normalizar nodos si se decide generalizar. | User, Place, Group, Event, Topic. |
| graph_edges | Relaciones persistentes consultables. | User VISITED Place, User MEMBER_OF Group. |
| edge_events | Historial de interacciones para sync futura. | User POSTED_IN Conversation at timestamp. |
| topic_tags | Temas detectados o elegidos. | japonés, skate, lectura, coworking. |
| user_topic_affinities | Afinidad calculada simple. | User interesado en japonés por mensajes/eventos. |

## 18. Stage 5A — Neo4j pilot
Neo4j entra cuando el grafo relacional empieza a quedarse corto para consultas profundas, recomendaciones explicables o visualización de relaciones. Neo4j modela datos como nodos, relaciones y propiedades, lo que encaja con usuarios, lugares, temas, grupos y eventos.
| Paso | Implementación | Criterio de aceptación |
| --- | --- | --- |

| Graph health | Conteo nodos/edges, fallos de sync. | Observabilidad básica. |

## 23. Modelo de datos evolutivo
### 23.1 MVP Supabase/Postgres
- profiles: identidad básica, safety_mode, avatar, bio.
- places: lugares físicos con lat/lng, radio, tipo y visibilidad.
- place_messages: chat público del lugar.
- local_groups y group_members: comunidades dentro de un lugar.
- local_events y event_attendees: planes nacidos desde lugar/chat.
- topic_tags y message_topic_tags: semántica inicial.
- safety_reports y user_blocks: seguridad desde el inicio.

### 23.2 Graph-ready relacional
- edge_events: stream de relaciones observadas.
- graph_edges: relaciones agregadas o persistentes.
- user_place_affinities: peso por visitas, mensajes y eventos.
- user_topic_affinities: peso por temas hablados o asistidos.
- place_topic_scores: identidad temática de cada lugar.

### 23.3 Neo4j / grafo dedicado
Nodos: User, Place, Group, Event, Topic, Conversation, MessageRef. Relaciones: VISITED, POSTED_IN, MEMBER_OF, ATTENDED, HOSTED_AT, MENTIONS, INTERESTED_IN, TRUSTED_BY, BLOCKED, CONNECTED_WITH.
Ejemplo conceptual:
User -[:VISITED]-> Place -[:HAS_GROUP]-> Group -[:HAS_EVENT]-> Event -[:MENTIONS]-> Topic

## 28. Riesgos y mitigaciones
| Riesgo | Impacto | Mitigación |
| --- | --- | --- |
| Chats vacíos | La app se siente muerta. | Pilotos concentrados en pocos lugares y eventos semilla. |
| Acoso/stalking | Alto riesgo de seguridad. | No ubicación exacta, safety mode, report/block, moderación. |
| Costos realtime | Escala cara o lenta. | Canales por place_id, paginación, límites, caching. |
| Grafo prematuro | Complejidad sin valor. | Postgres graph-ready primero; Neo4j solo con actividad suficiente. |
| UI demasiado clon | Riesgo legal/marca. | Inspiración de patrones, identidad propia, no assets ni copy exacto. |
| Replit vs mobile real | Preview falso positivo. | Expo Go/teléfono para QA mobile y ubicación. |

## 29. Definición de “app funcional de grafos”
Aldea se considera app funcional de grafos cuando cumple estos puntos:
- Las acciones sociales generan relaciones persistentes: usuario-lugar, usuario-tema, usuario-grupo, usuario-evento, lugar-tema.
- La UI muestra conexiones explicables, no solo listas cronológicas.
- Las recomendaciones usan relaciones, no solo filtros simples.
- Existe un backend de grafo dedicado o una capa graph-ready robusta en Postgres.
- El usuario puede entender por qué se le sugiere una persona, grupo, evento o lugar.
- El sistema mantiene guardrails de seguridad para no convertir el grafo en herramienta de stalking.

## 30. Próximo bloque recomendado
El siguiente bloque recomendado es cerrar R2C si todavía no está validado en Replit/GitHub. Inmediatamente después, ejecutar 1A con Supabase real o con fallback mock documentado. El primer hito de producto no es el grafo completo: es que dos usuarios puedan entrar al mismo lugar y conversar en realtime con seguridad básica.
