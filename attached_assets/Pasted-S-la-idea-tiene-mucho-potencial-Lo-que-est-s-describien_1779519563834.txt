Sí, la idea tiene mucho potencial. Lo que estás describiendo no es solo “chat por ubicación”, sino una red social geoespacial basada en grafos, donde cada espacio físico genera una comunidad, conversaciones, eventos y subgrupos con distintos niveles de acceso.

La diferencia clave frente a Nomadtable sería esta: Nomadtable está más orientada a viajeros, actividades cercanas, trips y meetups/eventos; su propia descripción habla de encontrar amigos viajando solo, unirse a actividades cercanas y conectar con personas en tiempo real.  ￼ Tu app sería más space-first: el centro no es el evento, sino el lugar vivo: parque, café, universidad, coworking, barrio, playa, plaza o biblioteca.

Una app en React Native donde cada espacio geográfico tiene un chat público propio, conversaciones persistentes, grupos comunitarios privados o semi-privados, eventos espontáneos y un grafo social que conecta personas, lugares, temas, conversaciones y relaciones.

Arquitectura recomendada

Para esta app yo no usaría una sola base de datos para todo. Haría una arquitectura híbrida.

Stack móvil

Capa	Tecnología sugerida
App móvil	React Native + Expo
Navegación	Expo Router o React Navigation
Mapas	Expo Maps / react-native-maps
Ubicación	Expo Location
Estado local	Zustand o Redux Toolkit
Chat tiempo real	Socket.IO o Firebase
Auth	Firebase Auth, Clerk o Supabase Auth
Push notifications	Expo Notifications
Moderación	API propia + IA/moderación textual
Backend	Node.js/NestJS o Fastify
Graph DB	Neo4j
Chat storage	Firestore, PostgreSQL o MongoDB
Cache/presencia	Redis
Media	S3, Cloudflare R2 o Firebase Storage

Socket.IO encaja bien para chats por salas porque sus “rooms” permiten emitir eventos a subconjuntos de clientes conectados.  ￼ Firestore también puede servir para updates en tiempo real con listeners sobre documentos o colecciones, aunque puede volverse caro o menos flexible si el chat escala mucho.  ￼

Por qué híbrida

Una base de datos de grafos como Neo4j es muy buena para modelar relaciones: personas, lugares, grupos, temas, eventos y conexiones. Neo4j se presenta precisamente como una plataforma para consultar datos conectados y visualizar relaciones complejas.  ￼

Pero guardar cada mensaje del chat como nodo principal puede volverse pesado si hay millones de mensajes. Mejor:

* Guardar mensajes en una base optimizada para escritura/lectura rápida.
* Guardar en Neo4j las relaciones importantes derivadas del mensaje.

Ejemplo:

El mensaje completo vive en Firestore/Postgres/MongoDB.

En Neo4j guardas:

* Usuario habló en lugar.
* Usuario mencionó tema.
* Usuario participó en conversación.
* Conversación generó evento.
* Usuario coincidió con otro usuario.
* Grupo pertenece a lugar.
* Evento ocurrió en lugar.

Eso hace que el grafo sea útil y no se vuelva una bodega infinita de texto.

Ejemplo de esquema Neo4j

CREATE CONSTRAINT user_id IF NOT EXISTS
FOR (u:User) REQUIRE u.id IS UNIQUE;
CREATE CONSTRAINT place_id IF NOT EXISTS
FOR (p:Place) REQUIRE p.id IS UNIQUE;
CREATE CONSTRAINT group_id IF NOT EXISTS
FOR (g:Group) REQUIRE g.id IS UNIQUE;
CREATE CONSTRAINT event_id IF NOT EXISTS
FOR (e:Event) REQUIRE e.id IS UNIQUE;
CREATE CONSTRAINT topic_name IF NOT EXISTS
FOR (t:Topic) REQUIRE t.name IS UNIQUE;

Crear usuario, lugar y conexión

MERGE (u:User {id: $userId})
SET u.displayName = $displayName,
    u.updatedAt = datetime()
MERGE (p:Place {id: $placeId})
SET p.name = $placeName,
    p.type = $placeType,
    p.lat = $lat,
    p.lng = $lng,
    p.radiusMeters = $radiusMeters
MERGE (u)-[r:VISITED]->(p)
SET r.lastSeenAt = datetime(),
    r.visitCount = coalesce(r.visitCount, 0) + 1;

Conversación pública de un parque

MERGE (p:Place {id: $placeId})
MERGE (c:Conversation {id: $conversationId})
SET c.type = "PUBLIC_PLACE_CHAT",
    c.visibility = "PUBLIC",
    c.createdAt = coalesce(c.createdAt, datetime())
MERGE (c)-[:BELONGS_TO]->(p);

Crear grupo local con seguridad

MATCH (p:Place {id: $placeId})
MATCH (owner:User {id: $ownerId})
CREATE (g:Group {
  id: $groupId,
  name: $name,
  description: $description,
  accessLevel: $accessLevel,
  createdAt: datetime()
})
CREATE (g)-[:BASED_IN]->(p)
CREATE (owner)-[:OWNS]->(g)
CREATE (owner)-[:MEMBER_OF {role: "OWNER", joinedAt: datetime()}]->(g);

Sugerir personas cercanas por lugar + intereses

MATCH (me:User {id: $userId})-[:INTERESTED_IN]->(topic:Topic)<-[:INTERESTED_IN]-(other:User)
MATCH (me)-[:VISITED]->(place:Place)<-[:VISITED]-(other)
WHERE other.id <> me.id
RETURN other, place, collect(topic.name) AS sharedTopics
ORDER BY size(sharedTopics) DESC
LIMIT 20;

Lógica de geolocalización

La app debería usar una combinación de:

1. GPS actual
2. Geofencing
3. Radio del espacio
4. Check-in manual
5. Última presencia válida
6. Privacidad por precisión reducida

Ejemplo:

type PlaceAccessContext = {
  userId: string;
  placeId: string;
  distanceMeters: number;
  isInsideGeofence: boolean;
  lastSeenAt?: string;
  trustScore: number;
};

Regla:

function canPostInPublicPlaceChat(ctx: PlaceAccessContext) {
  if (ctx.isInsideGeofence) return true;
  const wasRecentlyThere = ctx.lastSeenAt && minutesSince(ctx.lastSeenAt) < 60;
  if (wasRecentlyThere && ctx.trustScore > 0.6) return true;
  return false;
}

Esto evita que cualquiera desde lejos invada un chat local, pero permite continuidad si alguien acaba de salir del parque.

Conclusión

La idea es sólida porque mezcla tres cosas que normalmente están separadas:

1. Geolocalización
2. Chat/comunidad
3. Grafo social relacional

El punto más innovador es que no partes de “personas buscando eventos”, sino de lugares generando conversaciones. Eso puede sentirse más orgánico, más local y más humano.

La decisión técnica más importante: usar grafos para las relaciones sociales y contextuales, no necesariamente para almacenar todo el chat crudo. El chat puede vivir en una base optimizada para tiempo real, mientras Neo4j guarda el mapa inteligente de conexiones.

Siguiente paso recomendado: definir un MVP de 6 pantallas, elegir 2 o 3 espacios piloto y probar si los usuarios realmente conversan, crean grupos y convierten conversaciones en encuentros.
